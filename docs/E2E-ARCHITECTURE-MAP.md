# E2E Architecture Map — Viking Relay v0.4.3

> Generated by the E2E campaign (Phase 0). Evidence: source files cited inline; launch probe
> artifacts under `artifacts/e2e/probe/`.

## 1. Application type

**Electron desktop app** (Electron 43, electron-vite, React 19, TypeScript strict).
Single BrowserWindow (`1100x760`, min `820x560`), context-isolated sandboxed preload,
three bridge surfaces. Windows-only packaging (NSIS); tray integration on win32.

- Main entry: `out/main/index.js` (built from `src/main/index.ts`)
- Preload: `out/preload/index.js`
- Renderer: `out/renderer/index.html` (production) / Vite dev server via `ELECTRON_RENDERER_URL`

## 2. Process model

```
┌────────────────────────── Electron main process ──────────────────────────┐
│ AppSettingsStore (settings.json)   SecretStore (secrets.json, DPAPI)      │
│ Logger (pino → <userData>/logs)    AppUpdater (packaged only)             │
│ LoginItem (startWithWindows)       Tray (win32)                           │
│                                                                           │
│ ClientRelayService ── HTTP ──► REMOTE relay server (paired Server PC)     │
│ DirectDownloadsService (polls paired server every 5 s)                    │
│                                                                           │
│ ServerController                                                          │
│   ├─ JobEngine (states below) + gateways:                                 │
│   │    QbitTorrentGateway ── HTTP ──► qBittorrent WebUI v2 (config URL)   │
│   │    VikingGatewayAdapter ── HTTP ──► https://vikingfile.com (hardcoded)│
│   │    PackagingGatewayAdapter (ZIP on local fs)                          │
│   │    StoragePolicyGateway (volume free-space preflight)                 │
│   │    FsWorkspaceGateway (<dataDir>/jobs/<jobId>/)                       │
│   │    JsonJobRepository (data/job-history.json, atomic tmp+rename)       │
│   ├─ AuthController (pairing codes, bearer tokens, rate limits)           │
│   └─ RelayManager (Fastify; binds ONE non-internal IPv4 adapter address;  │
│        refuses 0.0.0.0; 5 s adapter watcher rebind/lost logic)            │
└──────────────┬────────────────────────────────────────────────────────────┘
               │ IPC (contextBridge): window.vikingRelay (shell)
               │                      window.vikingClientBridge (client mode)
               │                      window.vikingRelayServer (server mode)
               │                      push events on channel "server:event"
┌──────────────▼────────────────────────────────────────────────────────────┐
│ Renderer: shell App.tsx                                                   │
│   mode=null → ModeChooser → setMode('client'|'server')                    │
│   mode=client → client/App (Connect→Home→Metadata→Selection→Active→       │
│                 Complete/Error→History; friends; direct-download inbox)   │
│   mode=server → server/App (SetupWizard(5 steps)→Dashboard; PairingModal; │
│                 SendDirectModal; SettingsPanel; banners; history/archive) │
└───────────────────────────────────────────────────────────────────────────┘
```

Two product roles share one binary. A deployment is **two PCs**: a Server PC (runs relay +
qBittorrent + uploads to Viking file host) and one or more Client PCs (pair over Radmin VPN,
request torrents). E2E simulates both roles with two isolated app instances on one machine.

## 3. Persistence boundaries

| Store | Path | Format / notes |
|---|---|---|
| Settings | `<userData>/settings.json` | JSON, zod-validated defaults (`shared/settings.ts`) |
| Secrets | `<userData>/secrets.json` | DPAPI-encrypted hex entries; plaintext refused |
| Job history | `<dataDir>/job-history.json` | `{version:1,jobs[]}`, cap 100, atomic write |
| Job workspaces | `<dataDir>/jobs/<jobId>/` | torrent payload, ZIP artifacts |
| Direct jobs (server) | `<userData>/data/direct-jobs.json` | friend-send queue |
| Direct downloads (client) | `<userData>/data/direct-downloads.json` | received queue |
| Logs | `<userData>/logs/*.log` | pino |

`<userData>` is overridable per instance with the Chromium switch `--user-data-dir=<dir>`
(**verified by launch probe** — settings.json lands in the override dir; concurrent instances OK).

## 4. Job engine state machine (`src/main/jobs/types.ts:6-29`)

```
reading_metadata → awaiting_selection → queued → downloading
  → packaging (skipped for single-file direct upload) → uploading → finalizing → complete
failure at any stage → failed            user cancel → cancelled
in-flight job found at startup sweep → interrupted
```

Terminal: `complete | failed | cancelled | interrupted`. Retry endpoints are stage-specific
(`retry-packaging`, `retry-upload`, `recheck-storage`). Speed hints (waiting_for_peers/slow)
are presentation-only.

## 5. Relay HTTP API (server role, Fastify)

- `GET /v1/health`; `POST /v1/pair {code,name?}` → `{clientId,name,token}` (code TTL 10 min,
  max 5 active codes, per-IP 10 attempts/10 min, global 100/10 min; 429 w/ Retry-After)
- Bearer-token routes: intakes (`POST /v1/intakes`, `GET /v1/intakes/:id`),
  jobs (`POST /v1/jobs`, `GET /v1/jobs[/:id]`, cancel/retry-packaging/retry-upload/
  recheck-storage), `GET /v1/history?limit`, `GET /v1/server/status`, `GET /v1/clients`,
  direct-jobs (`POST /v1/direct-jobs`, `GET /v1/direct-jobs`, accept/decline).
- Port: `settings.serverPort` (default 47821). Bind host: selected adapter IPv4
  (Radmin-named preferred; explicit pin via `settings.radminInterfaceId`; refuses 0.0.0.0).

## 6. External integrations

| System | Endpoint control | E2E tier strategy |
|---|---|---|
| qBittorrent WebUI API ≥2.11.9 (key auth needs qbit ≥5.2.0) | `settings.qbittorrentBaseUrl` + secret `qbittorrent.apiKey` | Tier 1/2: local mock server (adapted from `tests/qbit/mock.ts`) |
| Viking file host | **Hardcoded** `https://vikingfile.com` in `server/composition.ts:buildVikingClient` | Tier 1/2: local mock + **new env seam `VIKING_BASE_URL`** (default unchanged); Tier 3 skipped (public upload of test junk = unwarranted external side effect) |
| Radmin VPN network | Adapter detection via `os.networkInterfaces()` | Real LAN IPv4 pin works locally (probe verified candidates exist) |
| electron-updater | Packaged builds only | Dev build ⇒ updater disabled (`UpdateState.disabled`) — asserted, not exercised further |

## 7. Environment / launch controls relevant to testing

| Control | Effect |
|---|---|
| `--user-data-dir=<dir>` argv | Isolates ALL persistence per instance (verified) |
| `ELECTRON_RENDERER_URL` | Dev renderer; also marks "dev" (updater disabled) |
| `RELAY_PORT` env | Parsed but overridden by `settings.serverPort` in composition — tests use settings |
| `VIKING_BASE_URL` env (**added test seam**) | Overrides Viking API base in `buildVikingClient` when set; default unchanged |
| `--hidden` argv | Tray-only start (login-item path) |
| Single-instance lock | Scoped to userData dir ⇒ isolated instances can run concurrently (verified) |

## 9. Critical end-to-end journeys (must be real-pipeline tested)

1. **J1 Pair & request**: Server setup → pair client → client submits magnet → metadata →
   select files → preflight → start → download(mock qbit) → package(ZIP) → upload(mock viking)
   → complete URL visible on BOTH UIs → persists across restart.
2. **J2 Cancel/race**: cancel during each active stage; double-submit; stale UI after cancel.
3. **J3 Failure & retry**: qbit down → failed; viking transient failure → retry succeeds;
   permanent failure → terminal failed with truthful error.
4. **J4 Friend direct-send**: server sends magnet to client B; client B accepts → direct
   download lands in client B's folder; decline path.
5. **J5 Restart/recovery**: kill mid-job → restart → interrupted sweep; completed history
   survives; pairing token survives restart.
6. **J6 Profile lifecycle**: reset profile (server), forget connection (client), revoke client
   → revoked client's requests get 401.
